# Exact transport optimization experiment — 2026-09-22

Initial benchmark status: **experimental, not enabled in the production runner**. The ongoing
SAKT/EdNet process was neither signaled nor restarted. Its production artifacts
were not edited. A separate ignored copy of its completed epoch-15 checkpoint
was used for these tests. This report is a performance diagnostic, not a new
scientific benchmark result.

## What changed in the candidate

- Construct the same rolling histories using vectorized CPU indexing.
- Pack 64 existing minibatches into one aligned byte buffer for host-to-device
  transfer. Unpack unchanged tensor dtypes, values, shapes, and batch boundaries
  on CUDA. This is **not** a larger training batch or gradient accumulation.
- Still perform one unchanged FP32 forward/backward/gradient-clip/Adam update
  for each original minibatch. Batch size remains 10 (including the original
  smaller bucket-tail batches), context/history remains 100/99, and all model
  hyperparameters and arithmetic remain unchanged.
- Buffer detached loss scalars, probabilities, and labels for 64 steps before
  copying to CPU. Retain the original sequential Python float loss summation
  and all seven metric definitions. No altered reduction or approximation.
- Preserve sampler order, seed 42, the DataLoader main-process RNG draw,
  dropout RNG, optimizer state, and checkpoint initialization.

No mixed precision, TF32 changes, compilation, fused optimizer, larger training
or evaluation batch, target removal, shorter context, or early-stopping change.

tolerance, including:

- every per-minibatch loss and every predicted probability/label;
- final model tensors and complete Adam optimizer state;
- Python, NumPy, PyTorch CPU and CUDA RNG state;
- all seven computed metrics;
- all input fields, PAD masks, shapes, and target IDs in every planned batch
  (checked separately before timing, including packing/unpacking).

Ten fixture tests additionally cover all three splits, histories 49/99/199,
empty history, mixed lengths, singleton/partial batches, repeated and reordered
requested indices, exact packing, and rejection of future timestamps.

## Limitations and adoption safety

- The live trainer continued sharing the H100 MIG device and CPU. Absolute
  times include contention; ratios are short-window measurements, **not a
  promise of full-epoch speedup**. No isolated-device experiment was run because
  that would require interrupting or moving the user's active training job.
- Timer includes loading/transfers/model steps/metric-array collection after
  warmup, but excludes common final scikit-learn metric calculation, checkpoint
  I/O, sampler-plan creation, and process startup. Full-epoch speedup may differ.
- This establishes exactness on the tested windows, not a mathematical guarantee
  for every future CUDA operation. Existing warn-only deterministic CUDA caveats
  still apply.
- The initial 64-step `transport_smoke.json` used whole-window metric buffering;
  it is retained as debugging provenance, not the reported estimate.
- The optimized utilities are separate from the production loader/trainer.
  The live process cannot simply adopt newly edited Python functions. Production
  integration, exact interrupted/resumed tests, and a safe handoff still need to
  be established before switching. **Do not kill the running process or discard
  its in-progress epoch to deploy this candidate.** Existing progress is intact.
